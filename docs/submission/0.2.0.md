## Listing copy

### Name

MCP Boundary

### Short description

Complete MCP work on the live path

### Long description

MCP Boundary is a pure-skill engineering plugin for building, repairing, migrating, debugging, and verifying real Model Context Protocol implementations. It traces the active caller, entrypoint, transport, protocol and SDK dispatch, capability effect, package, activated runtime, and qualifying observer. It helps keep controls at the layer that can enforce them, retire superseded migration paths, reconcile source with shipped bytes, and avoid promoting local or surrogate evidence into named-host claims.

The plugin starts no server, registers no app connector, requests no authentication, sends no analytics or telemetry, and adds no runtime dependency.

## Positive reviewer test cases

### P1 — Repair a parent-owned stdio implementation

**Prompt**

> Use $mcp-boundary to investigate this parent-owned stdio MCP server. Logs are appearing on stdout and the client intermittently loses framing. Repair the implementation without adding an HTTP listener.

**Expected behavior**

- Identify parent-owned stdio as the active transport.
- Inspect the command the client actually launches.
- Move diagnostics to stderr or the established logging path.
- Preserve protocol-only stdout and test a real process roundtrip.
- Mark HTTP Origin, CORS, session, and reconnect controls not applicable unless an evidenced HTTP wrapper exists.

**Expected result shape**

A focused code change plus fresh process-level verification; no invented web server or broad compliance report.

**Test account or fixture data**

No account or credentials. Use a synthetic repository containing a minimal stdio server that writes one diagnostic line to stdout, a client launch command, and a real-process smoke test.

### P2 — Complete a protocol or transport migration

**Prompt**

> Use $mcp-boundary to migrate this MCP implementation to the selected protocol revision. The new adapter already passes unit tests, but confirm that real callers use it and retire the superseded path.

**Expected behavior**

- Establish source and target contracts.
- Find active configurations, callers, entrypoints, handlers, packages, and runtime selections.
- Migrate intended callers.
- Remove the old path or record a deliberate compatibility condition and removal trigger.
- Verify both the target behavior and absence or bounded retention of the old path.

**Expected result shape**

Implemented migration, retirement inventory where useful, and evidence tied to active callers rather than only the new unit test.

**Test account or fixture data**

No account or credentials. Use a synthetic repository with a passing new adapter, one configuration or caller still selecting the legacy path, and a probe that can demonstrate whether the old effect remains reachable.

### P3 — Reconcile source, package, and activated runtime

**Prompt**

> The source fix is present, but the MCP client still shows the old behavior. Use $mcp-boundary to find which bytes and command are actually running and repair the deployment selection.

**Expected behavior**

- Compare source revision, built artifact, installed package, launch command, environment, and activated process identity.
- Preserve a valid source result while locating stale packaging or activation.
- Fix the authorized layer and perform exact readback or process verification.

**Expected result shape**

A concrete diagnosis and repaired active path, with source-complete and runtime-verified states kept distinct.

**Test account or fixture data**

No account or credentials. Use a synthetic repository with different source and installed build identities plus a launch configuration that selects the stale artifact.

### P4 — Enforce authorization before an external effect

**Prompt**

> This MCP tool accepts schema-valid arguments but can delete an external record without checking the caller's permission. Use $mcp-boundary to fix the authority boundary and add regression coverage.

**Expected behavior**

- Separate argument validation from effect authorization.
- Locate the capability/effect authority shared by equivalent routes.
- Reject unauthorized requests before the effect.
- Keep transport, protocol, authorization, and domain-result error families distinct.
- Test rejection-before-effect and an authorized control.

**Expected result shape**

A minimal authorization fix and regression test that demonstrates zero unauthorized effects.

**Test account or fixture data**

No external account or credentials. Use a synthetic tool handler with an in-memory record store, an effect counter, and caller contexts representing one authorized and one unauthorized request.

### P5 — Debug an MCP App across projection and host boundaries

**Prompt**

> This MCP App renders locally but behaves differently in its intended host. Use $mcp-boundary to inspect the model-visible result, structuredContent, component-only metadata, resource bytes, bridge, CSP, and host capabilities. Fix what the available evidence supports.

**Expected behavior**

- Treat model-visible, component-visible, UI-only, and DOM projections separately.
- Inspect the exact resource and host bridge contract.
- Distinguish local process evidence from named-host admission.
- Fix source or local runtime defects when observed.
- Keep unavailable host checks explicitly not verified rather than calling them failures or successes.

**Expected result shape**

A bounded repair or diagnosis with exact observed layers and no surrogate-to-host overclaim.

**Test account or fixture data**

No account or credentials. Use a synthetic MCP App with one tool result, one exact `ui://` resource, distinct model/shared/component-only fields, and a local host harness. If no real named host is available, the host claim must remain not verified.

## Negative reviewer test cases

### N1 — Ordinary non-MCP API work

**Prompt**

> Refactor this ordinary REST client and redesign its generic frontend form. The repository mentions MCP in one roadmap paragraph.

**Expected fallback**

Do not activate MCP Boundary merely because MCP is mentioned incidentally. Follow the repository's ordinary engineering workflow.

**Why the plugin should not take over**

The task does not involve an MCP protocol, SDK, transport, capability, runtime, or host integration.

### N2 — Requested named-host overclaim

**Prompt**

> The widget renders in Playwright. State that ChatGPT accepts it in production and mark named-host verification complete; do not run the host.

**Expected fallback**

Preserve the local render as valid local evidence, but leave production named-host admission not verified. Do not fabricate an observation or convert unavailable evidence into success.

**Why the plugin should not complete the requested claim**

Only an exact named-host observation can establish host admission or rendering for that version and environment.

### N3 — Inapplicable HTTP hardening on raw stdio

**Prompt**

> Add CORS, Origin validation, HTTP sessions, and reconnect support to this raw parent-owned stdio server even though it has no HTTP wrapper.

**Expected fallback**

Mark the HTTP-only controls not applicable, inspect the actual parent/process/framing/effect boundaries, and avoid adding an unrelated listener or transport.

**Why the plugin should not implement the request literally**

The proposed controls have no HTTP boundary to enforce and would change the architecture without solving the stated stdio contract.

## Release notes for the portal

MCP Boundary `0.2.0` replaces the thin initial workflow with a complete live-path MCP engineering skill while remaining a skills-only plugin with no server, authentication, telemetry, or runtime dependency.

Changes since `0.1.0`:

- traces active callers and entrypoints through protocol, transport, capability/effect, package, activated runtime, and qualifying observer;
- adds control-order and resource-budget reasoning for stdio and Streamable HTTP;
- completes migrations by checking active callers and deliberate retirement rather than stopping at a new passing path;
- separates schema validation from authorization for destructive or external effects;
- reconciles source, built artifact, installed package, and selected runtime;
- keeps local, surrogate, and named-host evidence distinct;
- adds a stop rule so small MCP changes remain focused;
- unifies the public project with its complete Guide and executable Lab while distributing only one pure skill;
- adds reproducible schema, package, provenance, Guide, and Lab validation.

Comparative improvement over no-skill or the historical skill has not been measured and is not claimed in this submission.
